# P8：动态 few-shot 实验

**结论：两种协议都得到 +4.0pt 的正向趋势，但都不显著。不能宣称"few-shot 让准确率提升了 4 个点"。**

## 做了什么

从题库里按 BM25 检索最相似的 3 道题，连同它们的**标准 SQL** 一起注入 prompt，
让模型模仿写法（SQL 示例比自然语言描述更能传达 join 结构和口径写法）。

```
## 参考示例（同类问题 → 标准 SQL，仅供模仿写法）
### 2025 年每个月的销售额分别是多少？
```sql
SELECT strftime(order_time, '%Y-%m') AS month, SUM(pay_amount) ...
```

用户问题：2025 年每个月的累计销售额是多少？
```

## 两种评测协议

示例池和评测集同源会有泄漏风险，所以做了两套：

| 协议 | 示例池 | 评测题 | 基线 | few-shot | 差值 | 95% CI | 显著 |
|---|---|---|---|---|---|---|---|
| A 同源 + leave-one-out | 全部 50 题（剔除自身） | 50 | 90.0% | 94.0% | **+4.0** | [−5.3, +13.3] | 否 |
| B 严格留出 | 25 题 | 另外 25 题 | 96.0% | 100.0% | **+4.0** | [+0.0, +12.0] | 否 |

- 配对 bootstrap，10000 次重采样
- 两组都是 3 次重复运行，标准差均为 0.0（temperature = 0，结果稳定）

## 变动明细（协议 A）

```
变好  h03  h07  h08  h13  m15   （5 题）
变差  h01  h15                 （2 题）
仍错  h05
```

变好的题里，`h08`（每月复购用户数）拿到了 `h12`（复购率）作为示例——
它没抄答案，但学到了"复购 = 有效订单 ≥ 2 笔"这个口径的写法。
示例与题目的 Jaccard 相似度都只有 0.2~0.6，不是近义改写。

## 为什么不显著

1. **样本太小**：50 题里差 2 题就是 4pt，二项分布的标准误约 4.2pt
2. **天花板效应**：留出集的基线本身就有 96%，只剩 1 题可提升的空间
3. **方向一致但不能算证据**：两种协议都 +4.0，更像是"有一点帮助"，
   但按我们自己定的规矩（CI 跨 0 即不下结论），这只能说"有正向趋势"

## 成本

| | prompt tokens / 50 题 | 相对 |
|---|---|---|
| 零样本 | 541,880 | — |
| few-shot=3 | 581,139 | **+7.2%** |

示例只占 prompt 的 2~8%（schema 有 3 万字符，占大头），所以 few-shot 的
token 代价很低——**如果它真有用，加得起**。

## 复现

```powershell
# 协议 A
python -m askdata.cli eval --strategy llm --fewshot 3 --repeat 3
# 协议 B（先切分，示例池只用 bank 那 25 题）
python -m askdata.cli eval --strategy llm --ids <test-ids> --repeat 3
python -m askdata.cli eval --strategy llm --ids <test-ids> --fewshot 3 --bank-ids <bank-ids> --repeat 3
```

## 下一步

要真正验证 few-shot，需要**更大的示例池**（比如 500 道题的 SQL 库），
最好来自真实查询日志而不是评测集本身。在 50 题的规模上，这类改动的效应
量级和噪声同阶，测不出来是正常的。
