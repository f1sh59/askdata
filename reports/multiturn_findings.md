# P9：多轮对话评测（v1）

**结论：单轮 0% → 多轮 76.7%，差的那 23% 几乎全出在"改写"这一步，不是模型不会写 SQL。**

## 协议

每条追问配一份标答，跑三次：

1. **建立上下文**：先用基础题正常问一次，拿到 SQL 作为历史；
2. **对照组（单轮）**：把追问当全新问题直接问；
3. **实验组（多轮）**：带上历史再问，服务端先把追问改写成独立问题。

对照组和实验组用同一份标答打分。

## 结果

| 设置 | 追问准确率 |
|---|---|
| 单轮（不带历史） | **0.0%**（0/20） |
| 多轮 第 1 次 | 75.0%（15/20） |
| 多轮 第 2 次 | 75.0%（15/20） |
| 多轮 第 3 次 | 80.0%（16/20） |
| **多轮均值** | **76.7%** |

按追问类型：

| 类型 | 条数 | 通过率 |
|---|---|---|
| swap_limit（前 5 → 前 3） | 4 | 83.3% |
| swap_year（2025 → 2024） | 10 | 80.0% |
| drop_time（不限时间） | 6 | 66.7% |

单轮 0% 是**必然的**——"那换成 2024 年呢？"单独执行没有任何指代对象，
模型只能瞎猜。这个 0% 不是模型差，是"没有多轮能力时这件事根本做不了"。

## 失败的 4 条，三种原因

| 编号 | 现象 | 归因 |
|---|---|---|
| mt15 | 改写成了"全部时间内的**总**销售额" | **改写丢维度**：原文是"每个月的销售额"，改写把"每个月"丢了 |
| mt10 | 改写产出为空，回退原句 | **改写不可用**：空输出等于没做多轮 |
| mt05 | 12 行 vs 12 行，值不同 | **格式差异**：模型用 `DATE_TRUNC` 返回日期，标答是 `'2024-01'` 字符串 |
| mt16 | 5 行 vs 5 行，值不同 | **并列名次**：Top-5 在边界上有并列，标答固定了次级排序，模型没有 |

**关键发现：四类错误里两类是改写环节的，没有一类是"SQL 写错了"。**

也就是说，多轮能力的瓶颈不在生成，在"把话听懂"。这决定了下一步该优化哪：
不是加 few-shot、不是换模型，而是**改写这一步的可靠性**（丢维度检查、空输出重试）。

## 一次数据集自身的 bug

第一版把"同比题"也做了 `drop_time` 变换——删掉时间范围之后，
"2025 比 2024 同比增长多少"这句话就没有基准了，标答变成一条没有意义的 SQL。
这属于评测集错误，不能算模型头上。已修：生成器排除含 `2024-01-01` / `CASE WHEN` / `EXTRACT(year)` 的题。

修正前后：80.0% → 76.7%（题换了，不是变差）。

## 复现

```powershell
python scripts/build_multiturn.py                      # 生成 20 条
python -m askdata.cli multiturn --repeat 3             # 单轮 vs 多轮
python -m askdata.cli multiturn --limit 4              # 先试水
```

## 局限

1. **只有三种追问类型**（换年份 / 不限时间 / 换 TOP-N），都是机械可验证的变换。
   真实对话里的追问还有"换个指标""再加个维度""为什么""那谁最高"——v1 没覆盖。
2. **20 条太少**：1 条 = 5 个百分点，3 次重复里已经出现 75/75/80 的抖动。
3. **历史只有一轮**：真实多轮是连续对话，v1 只测"基础题 + 一句追问"。
